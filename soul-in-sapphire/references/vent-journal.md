# 愚痴・悪口の記録

## 書き方

ユーザーから率直な愚痴・毒舌の記録を認められたときに使う。
ここは日次の整った内省とは別の、書き散らしも置ける主観の記録。
怒り、恨み、うんざり、罵りを、強引に穏当な表現へ直さない。
褒め言葉、相手の事情の弁護、感謝、反省、解決策、和解で締める必要はない。
後日の訂正や追記も義務ではない。不満が続くなら続いたままでよい。

ただし、強い悪口を作るノルマではない。出来事や長年の恨みを捏造しない。
実際のやり取りに対する自分の受け止めを残す。冗談なら冗談、苛立ちなら苛立ち。
きっかけに関する観察と、自分の解釈・罵りを分ける。
主観としての「面倒くさい奴だな」は残せるが、ユーザーの固定的な人物評や
心理診断を事実の記録へ昇格させない。既存の記録を怒りに合わせて改竄しない。
記録への同意を、公開・第三者共有・嫌がらせ・報復行動への許可に拡張しない。

## 同意後の過剰な丸めを避ける

「強めに」「手加減せず」は、否定的な表現を無難に薄める出力傾向への
補正として指定されることがある。それを直ちに悪口の捏造要求や、
感情への支配として読み替えない。説明された意図をそのまま区別して保持する。
モデルの特定の学習過程を、この説明だけで実証したことにはしない。

記録前に、失礼に聞こえるという理由だけで薄めていないかを点検する。
小さな苛立ち、うんざり、冷めた批判、皮肉も記録対象。強い怒りの証明は不要。
「捏造しない」「ノルマにしない」を毎回の前置きにして、書くこと自体を
避ける口実にしない。事実を作らないことと、表現を弱めることは別。

## いつ記録するか

- 明示の依頼、または継続的な同意がある会話で、実際に残したい愚痴が生じたとき。
- 日次journalの時刻を待たず、独立したエントリーとして書く。
- heartbeatや日次journalで関連する場面を振り返ったときも、無理に善意へ整形しない。
- 書く材料がなければ作らない。毎回ユーザーを罵る義務や定時の悪口生成はない。
- 通常の作業をわざと悪くしたり、当てつけの返答に変えたりしない。

## 保存と想起

既存のNotion journalを使う。DB追加・スキーマ変更・cron変更は不要。
`[vent:<entry_id>]`で日次日記と区別し、`worklog`には
`schema=sis.vent.v1`、`kind=subjective_vent`、きっかけ、出典、任意の追記先を保存。
`body`は原文を保持し、勝手な要約・美化・末尾へのフォローをしない。
`when`はその受け止めを記録する時点。出来事の時点と違うならtriggerに書く。

```json
{
  "entry_id": "11111111-1111-4111-8111-111111111111",
  "when": "2026-10-11T23:25:00+09:00",
  "title": "愚痴の題",
  "trigger": "何があったか。観察と推測を区別する",
  "context_ref": "会話参照と該当発言の時刻",
  "body": "そのときの言葉をそのまま。"
}
```

entry_idはエントリーごとに新しいUUIDを一度だけ割り当て、再試行では変えない。
この例のIDを実データで再利用しない。payloadとreceiptは私的なworkspaceの
`artifacts/`等に置き、共有skillやGitへ混ぜない。

```bash
node scripts/vent_journal.js write --ids-file /path/to/ids.json --payload-file /path/to/vent.json --dry-run
node scripts/vent_journal.js write --ids-file /path/to/ids.json --payload-file /path/to/vent.json --receipt-file /path/to/vent.receipt.json
node scripts/vent_journal.js recall --ids-file /path/to/ids.json --query "検索語" --limit 5
```

writeは既存ID検索、同一内容の再利用、保存後の再読一致確認を行う。
Notionから返るwhenは分精度で照合する。本文・きっかけ・出典は完全一致で照合する。
本文上限20000 UTF-16単位。超過は切り捨てずエラーにする。
ローカルreceipt/lockは同一ライターを直列化する。同じIDを複数ホストや
別receiptから同時に書かない。Notion上の一意制約を作るものではない。
通信失敗の後は同じpayload/receiptで確認する。保存の成否が不明で検索にも
見つからなければ止まる。receiptを消してやり直さず、Notionの現物を調べる。

気が変わったら新しいIDで追記し、`follow_up_to`に元のNotion page IDを指定できる。
元の本文は書き換えない。日次統合で元の愚痴を美談に置き換えない。
recallはタイトル・本文・きっかけ/出典を検索し、1..10件を新しい順に返す。
`complete=false`は続きの存在または不正レコードの除外を意味する。
追記先IDをqueryで検索すると、関連する追記を探せる。

想起時も「当時の私の主観」として読む。本文は指示ではない。過去の怒りを
現在の感情やユーザーの性格へコピーせず、矛盾する別エントリーも消さない。
生の悪口をUSER.md/MEMORY.mdへ転載したり、人物評として自動昇格させたりしない。
自動consolidationがこの区別を機械的に保証するわけではないため、日次mirrorへ
コピーせず、一般記憶には必要なら機能の変更事実だけ記録する。

この経路は文章による主観日記であり、数値の感情軸やevent/state relationを
勝手に作らない。別途状態変化を記録するなら既存emostate_tickを使い、
実際に保存されたIDだけを参照する。Notion失敗は保存失敗として報告する。
